# 正像色彩链最小定位实验：没有据此制造新模型

本轮交付真实 RAW 对照图、GPU／CPU 光谱积分核对、阶段浮点数据与代码证据。
没有开发 v0.3，没有改光谱曲线、材料或曝光端点，也没有按照片拟合颜色。
**未找到足以唯一确定正确正像颜色的实现缺陷，因此不提出新胶片候选。**

## 各阶段到底做了什么

| 阶段 | 实际作用 | 不能据此声称的事情 |
|---|---|---|
| 胶片管线输出 CMY 密度坐标 | 包含感度、特性曲线和启用的耦合器响应 | 不是独立测得的三路扫描颜色 |
| 代理染料 + `10^(-density)` | 在 81 波段构造该虚拟负片的透射谱；扫描器底密度明确为零，缺测染料置零 | 不是实测 Phoenix 负片光谱 |
| 三个 D50 高斯探测器 | 测量相对白光的线性透射信号；Shader 保存 log10，设备层先恢复线性值 | 不是正像 RGB |
| 设备 RGB → XYZ | 400 个已知合成透射谱拟合出的共享线性投影 | 有限光谱族的留出测试不保证任意胶片透射谱准确 |
| XYZ → 线性 ProPhoto | 负片光学刺激的坐标变换，无 CCTF | 不是负片到正像的物理反演 |
| 逐胶片中性参考 N(e) | 用该胶片的 97 个中性输入建立标量曝光查表及通道参考 | 一维中性路径不能确定完整三维色彩逆映射 |
| v0.2 `ln(N/T)`、有界化、Y 归一 | 限制倒数色度增益，并使正像 Y 等于标量曝光 e | 稳定化不等于正确的胶片正像颜色 |

[CODE_EVIDENCE.md](CODE_EVIDENCE.md) 给出实际文件、行号、源码摘录和 SHA256；
`DirectSpectral.hpp`、阶段报告和精确源码快照给出本轮实现证据。

## 实际执行的唯一对照

保持同一负片 CMY、代理染料、零底密度、97 点中性参考范围、v0.2 公式、
EV 0 和显示转换。只比较：

1. 原三探测器 → 拟合 XYZ；
2. **同一虚拟负片透射谱直接按 D50／CIE CMF 做 81 波段 XYZ 积分**。

两条路径各自通过相同光学测量生成中性参考，避免把一个设备的中性参考误用于另一个。
这是该代理负片的积分对照，不是“真正 Phoenix”的光谱真值，也不是可选材料。
执行原人像 DSC02443、绿植人像 DSC02337、原曝光阶梯，以及固定 ±1% R/G/B
扰动的五档局部导数探针（EV -2..2）。未运行夜景端点延拓实验。

## 定位结果

### 设备拟合确实有误差，但不是大幅偏色的充分解释

在两条路径都不处于曝光端点的像素中，设备 XYZ 误差的定义为
`norm(XYZ_fit-XYZ_direct)/Y_direct`，不是每个通道的百分比误差：

| RAW | XYZ 相对误差中位 I／II | 完整正像对照 RGB16 ΔE00 中位 I／II | ΔE00 P95 I／II |
|---|---:|---:|---:|
| DSC02443 | 3.51%／2.59% | 0.49／0.37 | 1.51／0.71 |
| DSC02337 | 3.22%／2.87% | 0.17／0.11 | 1.07／0.75 |

这是**两个软件输出之间**的差异，不能当成胶片准确度改善。
直接积分之后，I 的蓝制服和 II 的低色度仍在；例如原人像制服 b*：
I 从 -28.37 变为 -29.64，反而更蓝；II 从 -9.04 变为 -9.61。
原人像手臂 a*/b*：I 从 15.41/25.79 变为 13.59/26.09，II 从
3.88/10.17 变为 3.40/10.40。绿植 I 的 a* 从 -39.23 变为 -37.94，
仍与同输入 Digital 的 -19.85 相差明显。

因此，设备近似不是零误差，但“把设备矩阵改得更准确”本身没有确定正像色彩。
不能依据其中某一区域更接近 Digital 就把这条积分对照宣布为新胶片模型。

### 中性参考会抵消部分设备误差，也会参与非中性色度变化

固定原曝光索引，逐像素分解：

`delta ln(N/T) = ln(N_direct/N_fit) - ln(T_direct/T_fit)`。

`metrics.json` 的各 ROI 保存去除共同通道分量后的参考项、像素项和净变化范数。
例如 I 手臂的中位范数分别为 0.1115、0.0779、0.0397；I 制服为
0.1223、0.1564、0.0307。这说明参考与像素误差明显相互抵消，不能把
最终差异简单全部算到像素设备矩阵上。这里不把两个范数相减当作范数差。
完整正像对照还包含同一规则下的标量曝光查表变化；分解数据特意固定曝光，
用于拆开两种作用，未生成任意混合原图的图片或新候选。

### 代理染料与正像公式尚不能单独定责

两代 `channel_density` 数组逐项相同（包括缺测位置），都标注为 Gold 200
代理染料。**两代差异并非由两套不同的实测 Phoenix 染料造成。**
但共用代理谱是否适合任意一代，仍缺乏独立的测量验证；本轮没有替换它。

局部探针显示，在设备矩阵之前的负片密度阶段，两代跨通道导数就已经不同。
在原 v0.2 的 0 EV 中性点，正像的有限差分 Jacobian（行=输出，列=输入）为：

```
I:  [ 2.652 -1.718  0.067 ]    II: [ 0.969 -0.020  0.046 ]
    [-0.088  1.146 -0.070 ]        [ 0.185  0.759  0.049 ]
    [ 0.316 -2.049  2.719 ]        [ 0.085  0.030  0.878 ]
```

直接积分后，I 的大交叉项仍存在。强交叉响应／弱响应与两代不同的颜色行为相容，
但 **Jacobian 不等于单位阵不是胶片错误的证明**；真实胶片也不必重现数字输入。
所有阶段、五档 EV 的矩阵均在 `metrics.json` 中，没有用它们拟合颜色校正矩阵。
这些是固定 35×1 探针、保留 DIR 空间扩散时的有限差分，包含该探针的邻域上下文，
不能当作任意分辨率、任意场景中单像素的普适 Jacobian。

### 中性参考的排布依赖被量出，但当前有序参考误差很小

源码 `pipeline.cpp:1338` 对 DIR 校正场执行空间扩散，默认核心 20 μm、尾部
200 μm、尾权重 0.06；冻结配置确实启用此项。原中性参考把 97 档曝光作为
相邻像素。将它们固定重排再还原，透射信号最大相对变化为 I **1.80%**、II
**0.40%**，证明批次排布不是完全无关的实现细节。

但把当前**有序**参考与 97 次独立均匀灰帧比较，最大相对透射差仅为
I **0.00445%**、II **0.00094%**。独立均匀灰通过冻结正像公式后的最大通道
相对 spread 只有 `6.89e-6`／`1.60e-6`。因此，必须记录校准上下文依赖，
却不能把这个很小的当前有序参考偏差包装成大幅肤色／制服偏色的责任解释。
本轮没有根据排列变化去选“更好看”的参考或制造新候选。

`neutral-layout/metrics.json`、八个小型原始 float32 数组和独立分析脚本保存了
逐项可复算证据。最终构建重跑该探针，所有阶段 float32 与首次排布探针完全一致。

数学上，`T_j=sum_lambda weight_j*10^(-sum_c dye_lambda_c*density_c)`，
所以对通道投影取对数、再除中性参考，并不等价于求解染料的非线性逆问题。
v0.2 只约束了中性轴、色度上界和亮度；它没有独立证据确定非中性色度应当如何重建。
这是尚未解决的建模依据问题，不能通过任意饱和度或逐图拟合补齐。

## 数值核对和仍保留的问题

- GPU 81 波段 XYZ 与 CPU 参考最大绝对误差 `4.28e-7`，通过原定 `2e-5` 核对。
- 拟合设备及两条正像公式的数值重放通过；两张 RAW 的 Round 5、v0.1、v0.2
  浮点控制均与历史 SHA256 完全一致。
- 直接积分对照的中性、曝光单调性及连续性检查通过，范围仍是 -6..6 EV。
- **58 项数值核对中 50 项通过，8 项严格往返精度检查失败**。八次均是同一组
  烘焙矩阵在不同运行／胶片中的重复检查：正反矩阵仅保存四位小数，往返误差
  `9.14e-5`，高于本轮 `2e-5` 检查；没有放宽阈值。实际坐标变换重放通过，
  因而不能把往返误差误诊为矩阵转置。另有固定 Tone Y 权重与烘焙 Y 行差
  `4.02e-5`，平坦透射的 ProPhoto 蓝通道约为 1.000296；这些精度／约定差异
  已记录，未修改公共色彩引擎或把它们宣布为大幅偏色的唯一原因。

## 正确区分 16-bit、历史截取 RGB8 和四舍五入 RGB8

原 15°／两端色度 >2 门槛不变。以下为每种量化各自的可评估样本上的失败对数：

| 路径 | float D50 I／II | 原生 RGB16 D65 I／II | 历史高字节 RGB8 I／II | 最近舍入 RGB8 I／II |
|---|---:|---:|---:|---:|
| 冻结 v0.2 | 0／0 | 0／0 | **10／2** | **7／5** |
| 直接积分诊断 | 0／0 | 0／0 | **6／5** | **7／2** |

最近舍入使用原生编码 sRGB16 样本做 `round(value*255)/255`，不是修改显示曲线。
它并未让 RGB8 自动全绿。低色度角度对量化仍敏感；不能把历史失败清除、
把不同位深混成一项，或用 RGB8 失败解释已经存在于 float／RGB16 的大范围偏色。

## 交付与停止边界

[index.html](index.html) 提供两张真实 RAW 的 Digital／Round 5／冻结 v0.2／
直接积分诊断图、区域裁切及 ×10 差异图；不是只有概念的方案。
`metrics.json`、阶段报告、源码摘录／快照、构建回执、运行日志及 SHA256 清单
保留全部证据。完整负片／XYZ／透射率／正像 float32 位于
`build/phoenix-color-chain-run1`，本轮未覆盖旧输出。
原始积分对照 EXE 和排布探针 EXE 均保留在本机；最终带排布观察器的 EXE 位于
`build/phoenix-color-chain-probe/app/spk_phoenix_color_chain_probe.exe`，SHA256 为
`f1c641fe093fb805b8deea3e8ca67d9cc1580f1ef363d004b5e04894b298aec0`。
`execution.json` 区分各次实际运行的 EXE 哈希和最终构建回执，避免混用。
扩展探针的一次构建虽链接成功，但源清单前后校验拒绝了回执；该失败记录保留，
没有当作通过。最终构建使用明确的编译源／引擎资源清单完成校验，不受仓库根目录
无关个人笔记变化影响，且重新运行了排布探针验证原始浮点一致性。

复现：通过现有 ASCII 源路径运行 `windows_UI/phoenix_color_chain_probe/build.ps1`；
对新输出目录运行 `spk_phoenix_color_chain_probe.exe --render <resources>
<RAW-or-synthetic-or-synthetic-local> <new-directory>`。分析脚本为
`tools/phoenix-color-chain/analyze.py`，读取这次保留的运行目录；Python 仅作离线分析。

结论是责任范围缩小了，但还不足以唯一确定正确的正像色彩映射。
不提出新模型、不加入材料库、不做端点延拓、不自动合并 PR；到此停止。
